# Terminology and writing conventions

## 1. Scope

This document defines the vocabulary used in manuscripts, technical reports, research plans, experiment records, figure captions, and repository documentation. Academic concepts must use terms established in the relevant research community. New project-specific names must not be introduced for concepts that already have accepted names.

Exact source-code identifiers may be retained in code font when needed for reproducibility. They must be followed by an established technical description and must not be presented as new scientific terminology.

Exact paper titles, short quotations, command-line options, serialized field names, file names, and immutable experiment artifacts must retain their source form. This exception preserves citation and computational provenance; it does not authorize using those strings as manuscript terminology. Dated reports may describe an obsolete implementation, but their current explanatory prose must still use established terms.

## 2. Rules

1. Use one established term for one concept throughout the repository.
2. Do not turn an ordinary observation or comparison into a named framework, principle, effect, score, taxonomy, or diagram.
3. Define new mathematical contrasts with equations and plain descriptions. Do not assign them new conceptual names unless that name is already used in the literature.
4. Refer to every compared evaluation procedure as a `method`.
5. Use the exact names of established methods, such as system identification, symbolic regression, adaptive experimental design, non-adaptive experimental design, matched-pairs design, factorial design, process evaluation, held-out evaluation, and sensitivity analysis.
6. Use `development set`, `validation set`, `test set`, and `private test set` according to their standard meanings. Do not replace them with project-specific alternatives.
7. State what was measured. Do not infer memorization, reasoning, scientific understanding, or non-exposure from performance alone.
8. When no accepted community term exists, describe the operation literally instead of inventing a short label.
9. A proposed term that is not present in the terminology table requires a literature source and explicit approval before use.
10. Project names and implementation identifiers are proper names, not scientific constructs. Use them only when exact identification is necessary.
11. In manuscript prose, headings, captions, table text, and footnotes, do not use sentence-level dashes, colons, semicolons, or question marks. This applies to both English and Chinese punctuation. Rewrite the sentence with a period, comma, or conjunction instead. Preserve symbols that are part of a word, established phrase, or proper name, such as `Prior-only` and `GPT-5.5`. Write date ranges with `through` or `to`. This rule was explicitly requested by the user on 2026-09-20. LaTeX references, link destinations, Markdown table separators, and other non-rendered syntax are not prose punctuation and must remain functional.

## 3. Canonical terminology

| Canonical term | Meaning in this project |
| --- | --- |
| benchmark instance | One executable evaluation problem |
| task family | A group of related benchmark instances |
| historical condition | The condition whose data-generating relation follows the historical reference law |
| counterfactual condition | The matched condition with one prespecified change to the data-generating relation |
| temporal evaluation | Evaluation on benchmark instances derived from recent papers |
| source-reported condition | One condition or regime explicitly reported in a source paper |
| system identification | Estimation within a disclosed model class |
| scientific law discovery | Recovery of a predictive relation when the model class is not disclosed |
| symbolic regression | Search for a symbolic expression that predicts observed data |
| prior-only baseline | Evaluation without experimental observations |
| fixed experimental design | A prespecified, non-adaptive set of experiments |
| adaptive experimental design | Sequential selection of experiments using previous observations |
| evaluation method | One compared evaluation procedure |
| matched-pairs design | Comparison of paired historical and counterfactual conditions within a task family |
| factorial design | Crossed experimental factors analyzed through main effects and interactions |
| held-out evaluation | Evaluation on observations not provided during model fitting or interaction |
| process evaluation | Evaluation of observable actions and outputs during an interaction |
| data-generating process | The function or simulator that produces observations |
| simulator-based oracle | An interface that returns observations generated by a fixed simulator |
| LLM-based oracle | An oracle whose response is generated by a language model |
| LLM-as-a-Judge | Use of a language model to evaluate recorded outputs |
| Prediction score | Continuous numerical accuracy within one episode, computed as one divided by one plus the mean tolerance-normalized error. Group summaries use available scores and report their count |
| Episode success rate | Successful episodes divided by all planned episodes in the reported group. Unfinished episodes count as failures. Reported as a percentage with abbreviation ESR |
| Explanation score | Mean of the LLM judge's three criterion scores for the last selected scientific response in an episode. Missing if any criterion is unassessable and separate from episode success |
| model checkpoint | A fixed set of model weights |
| model snapshot | A versioned API model configuration when weights are unavailable |
| training-data cutoff | The documented end date of training-data collection, with stated uncertainty |
| benchmark contamination | Inclusion or exposure of evaluation material in training or tuning data |
| temporal contamination audit | Benchmark-instance-by-model documentation of publication dates, model cutoffs, access, and exposure |
| prompt paraphrase | A meaning-preserving reformulation of a prompt |
| sensitivity analysis | Analysis of how results change under alternative justified specifications |
| preregistration | A protocol and analysis plan fixed before observing evaluation outcomes |
| primary outcome | The prespecified outcome used for the main inference |
| secondary outcome | A prespecified supporting outcome |
| exploratory analysis | Analysis not designated as confirmatory before outcome inspection |

## 4. Repository identifiers

The following names are implementation identifiers. They may appear exactly as written in code font, but prose must explain them with the canonical terminology above.

| Identifier | Standard description |
| --- | --- |
| `BenchmarkCase` | executable benchmark instance |
| `MatchedFamilySpec` | specification for a matched task family |
| `Player` | evaluated language-model agent |
| `Oracle` or `CaseOracle` | experimental interface |
| `WorldModel` | benchmark simulator or data-generating process |
| `IDENTIFICATION` | system-identification task setting |
| `DISCOVERY` | scientific-law-discovery task setting |
| `predictive_model_pass` | binary held-out prediction outcome |
| `experiment_discriminativeness_mean` | implementation metric based on separation among the agent's pre-experiment predictions |
| `evidence_aligned_belief_update_rate` | implementation metric comparing reported hypothesis weights with subsequent prediction errors |

These identifiers do not establish that the associated academic construct has been validated. In particular, an implementation metric must not be renamed as a measure of reasoning, understanding, Bayesian updating, or scientific competence without independent validation.

## 5. Review procedure

Before a document is treated as current:

1. compare its recurring technical terms with this file;
2. search for prohibited expressions;
3. preserve exact code identifiers only in code font;
4. verify that mathematical contrasts are defined rather than named;
5. check that claims use the terminology of the cited literature;
6. record unresolved terminology in the document instead of inventing a replacement.
7. check rendered manuscript text for prohibited punctuation, retaining only the word-internal and name-internal exceptions in Rule 11.

Changes to this terminology table require a source, a reason, and a repository-wide consistency check.
